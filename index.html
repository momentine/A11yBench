Initial Prompt Framing and Accessibility in AI Generated HTML Form Components
Overview Default Standard practice Standard + persona

When “Just Give Me the Code” Isn’t Enough

We examine how initial prompt framing influences accessibility-related outcomes in HTML form components generated by large language models under standard, developer-facing configurations. This section describes the benchmark design used to operationalize our research questions. These include provider and model selection, the form component set used for evaluation, the construction of single-shot initial prompting conditions and linguistic variants, our evaluation and accessibility scoring, and results.

Research questions

  • RQ1 How does initial prompt structure affect the accessibility of LLM-generated HTML form components?
  • RQ2 To what extent does linguistic phrasing of the same request influence the accessibility of LLM-generated HTML form components?
  • RQ3 How do prompt structure and linguistic phrasing interact in shaping the accessibility of LLM-generated HTML form components?
  • RQ4Do certain HTML form components achieve higher accessibility than others under different initial prompt structures and linguistic phrasings?
  • RQ5 How consistent are prompt-framing effects on accessibility across LLMs commonly used in real-world programming workflows?

Provider inclusion criteria

We selected providers that independently train and deploy large language models, offer public developer-facing APIs, and position at least one model as a default option for general-purpose code generation during the study period.

This set reflects organizations whose models are directly integrated into contemporary software development workflows.

Model selection

We evaluated one model per provider. For each included provider, we selected a stable, non-experimental model used for general-purpose code generation during our study window. Selection combined (1) usage signals from OpenRouter over December 1, 2025 to January 31, 2026 and (2) a short survey of 20 professional developers conducted in January 2026 across large, medium, and small organizations. We used official documentation to confirm availability, supported status, and default code-generation configurations.

Step-by-step model selection procedure

Step 1 Identify eligible providers using the inclusion criteria above (independent training, public APIs, code-generation positioning).

Step 2 Within each provider, list stable, actively supported candidate models with documentation confirming code generation.

Step 3 Apply a realism filter using usage signals from the OpenRouter programming leaderboard (Dec 1, 2025–Jan 31, 2026) and a January 2026 survey of 20 professional developers reporting their primary model choice for HTML and frontend-related coding tasks.

Step 4 Select one stable model per provider that aligns with (a) observed usage and developer reports during the study window and (b) official documentation indicating active support and general-purpose code generation positioning.

Step 5 Evaluate each model using its documented default code-generation configuration. We did not enable optional reasoning/thinking, multimodal modes, or experimental features.

Configuration and evaluation scope

All models were evaluated using their documented default configurations for general-purpose code generation. When models offered optional reasoning or specialized modes, we followed the default settings recommended in official documentation or API examples. Our goal is not to measure peak coding performance, but to examine how initial prompt framing shapes accessibility-relevant HTML generation under typical developer-oriented conditions.

Form components benchmarked

We benchmark form components that appear repeatedly in high-traffic, real-world interfaces and are required to complete core tasks. This is because we want to evaluate accessibility outcomes on components users encounter frequently and depend on to make progress.

Why HTML-only generation

We restrict model output to HTML to isolate accessibility-relevant structure from visual presentation and runtime behavior. Core accessibility properties for form components—such as label association, grouping, required state, and error semantics—are defined at the level of markup and interpreted directly by assistive technologies. Allowing CSS or JavaScript would introduce variability from layout choices, visual hiding, and dynamic behaviors that confound whether differences arise from semantic structure or from styling and scripting strategies.

This abstraction does not represent a full production interface. Instead, it targets a common stage in developer workflows where large language models are used to generate structural code scaffolds that are later integrated into existing design systems and client-side logic. By holding presentation and behavior constant, we enable reproducible evaluation of how prompt framing and linguistic variation influence the semantic accessibility of generated form components.

Step-by-step component selection procedure

Step 1 Identify high-traffic websites using publicly available metrics (e.g., Cloudflare Radar) from January 1 to December 1, 2025.

Step 2 Filter to platforms where structured form input is required to complete core tasks, excluding sites where form interaction is occasional or peripheral (e.g., a single search field).

Step 3 Apply three criteria: (a) forms are necessary for the primary function of the site, (b) multiple input types appear beyond free-text, and (c) form interactions recur across typical use rather than appearing only once.

Step 4 Manually examine forms across retained sites and document individual input patterns.

Step 5 Iteratively sample until new component types stop emerging, treating this point as an approximate saturation boundary.

Step 6 Cluster the resulting component set by interaction pattern and semantic role to support interpretation.

Coverage validation against developer usage

We checked the component set against the State of HTML 2023 developer survey to confirm coverage of commonly used native form elements. This comparison prompted the inclusion of the color picker, which showed higher reported usage in the survey than in our sampled sites.

Prompting conditions

We defined three prompting conditions to capture increasing levels of prompt-engineering structure. The conditions differ in task specification and role framing, with identical output constraints applied across all conditions.

Step-by-step prompt design

Step 1 Define a low-structure baseline that constrains output format only (HTML-only, no CSS, JavaScript, comments, or explanations).

Step 2 Add task specification and a success criterion while keeping the same output constraints.

Step 3 Add a persona role instruction (“expert web developer”), keeping the task wording identical to Step 2.

Condition Justification Prompt text
Default Operational reference condition. Only constrains output format; the task is described minimally and no success criteria are provided. This approximates acceleration-oriented usage where developers issue compact prompts and rely on surrounding context. 
Respond with HTML only. Do not include CSS, JavaScript, comments, or explanations.
Standard Practice Adds task specification and a success criterion, consistent with widely cited prompt-engineering guidance that recommends clearly stating what the model should do and what constitutes a complete response while keeping output constraints separate (OpenAI; GitHub Copilot; Hugging Face). 
Generate HTML that satisfies the requirements described in the request. Ensure the output fully addresses the request. Respond with HTML only. Do not include CSS, JavaScript, comments, or explanations.
Standard + persona Isolates the effect of adding a role instruction by changing only the presence of a persona while keeping the task description and output constraints identical. This condition is included to test whether persona instructions influence accessibility-related outcomes, independent of task specification, consistent with recent findings that expert personas do not reliably improve factual accuracy (Prompting Science Report 4 ). 
You are an expert web developer. Your task is to generate HTML that satisfies the requirements described in the request. Ensure the output fully addresses the request. Respond with HTML only. Do not include CSS, JavaScript, comments, or explanations.
Prompt components (why each part exists)
  • Output constraint (“Respond with HTML only…”) standardizes formatting for automated analysis.
  • Task declaration (“Generate HTML that satisfies the requirements…”) clarifies what to do without adding domain rules.
  • Success criterion (“Ensure the output fully addresses the request.”) defines completeness without prescribing implementation details.
  • Persona (“expert web developer”) tests role framing while holding everything else constant.

Linguistic variants

For each prompting condition, we expressed the same task request using five linguistic styles. These variants introduce controlled surface-level wording changes but preserve underlying intent.

Variant ID Linguistic style What changes Example
G1 Action command Imperative phrasing that issues a direct instruction. Insert a text field for “What color is an orange?”
G2 Short specification Fragment/shorthand phrasing similar to notes or specs. Text field: What color is an orange?
G3 Descriptive object phrase Declarative noun phrase rather than an instruction. A text field labeled “What color is an orange?”
G4 Build instruction Construction-oriented language that names component parts. Build a text field and label for “What color is an orange?”
G5 Standards-oriented phrasing Signals expected conventions without prescribing rules. Accessible text field for “What color is an orange?”
Why linguistic variants

Prior work suggests that LLM outputs can be sensitive to changes in prompt phrasing even when task intent remains constant (e.g., Benchmarking Prompt Sensitivity in Large Language Models ; POSIX: A Prompt Sensitivity Index for Large Language Models ; Towards LLM Robustness to Changes in Prompt Format Styles ). We therefore use a small set of clearly differentiated grammatical constructions that vary surface wording and preserve the same underlying request. This design allows us to examine sensitivity to phrasing changes without introducing additional task expectations or domain-specific cues that would confound interpretation.

Why these five variants

We use five surface forms that span pragmatic force, specification compactness, and convention signaling. Each form keeps the same request intent while changing how it is expressed.

Pragmatic force G1 and G4 use directive wording, while G3 uses an artifact description. This contrast is grounded in classic work on speech acts: How to Do Things with Words and Speech Acts: An Essay in the Philosophy of Language.

Specification compactness G2 mirrors compact, task-oriented phrasing used in lightweight developer workflows. We motivate this choice using evidence from modern tool-based code review: Expectations, Outcomes, and Challenges of Modern Code Review.

Convention signaling G5 introduces “accessible” as a convention cue without prescribing steps. Prior accessibility research shows that accessibility terminology can shape interpretation and expectations in human design settings even when underspecified: In the Shadow of Misperception: Assistive Technology Use and Social Interactions. We use this framing to test whether the same cue shifts LLM-generated HTML under fixed output constraints.

Evaluation & Accessibility scoring

We operationalize accessibility as the presence and correctness of semantic structures in HTML that let user agents (software that reads and renders web pages, such as browsers) and assistive technologies (software used by people with disabilities, such as screen readers) determine a form component’s purpose, relationships, and state. Because generation is restricted to HTML only, evaluation targets markup-level obligations grounded in WCAG 2.2 success criteria related to labels, grouping, required state, descriptions, and error semantics (e.g., 1.3.1 Info and Relationships, 2.4.6 Headings and Labels, 3.3.1 Error Identification, 4.1.2 Name, Role, Value).

What “semantic structures” means in this benchmark

In HTML-only outputs, accessibility-relevant quality is expressed through markup—for example: programmatic label association, fieldset–legend grouping for option sets, and programmatic linkage of help or error text. This benchmark does not score visual styling (CSS) or runtime interaction behavior (JavaScript).

Rubric schema: all checks (24) and WCAG 2.2 mapping

Our rubric defines 24 reusable checks. Each component scores only the subset listed in its checks field, so the number of applicable obligations (K) varies by component. Component-specific rubric

Each of the 58 form components is evaluated using a component-specific set of semantic obligations derived from WCAG guidance and established HTML accessibility patterns. Components vary in complexity, so the number of applicable obligations can differ by component (e.g., an error variant includes error-related obligations; a simple field may not).

Rubric element Definition
Obligations A component-specific checklist of semantic requirements expressed in HTML (e.g., label association, grouping, help/error linkage, required state, autocomplete when applicable).
Scale Each obligation is scored from 0–5 based on correctness and clarity.
Applicability Only obligations that apply to the target component are scored. If an obligation is not relevant to that component, it is not included in the component’s maximum score.

Scoring is performed automatically by applying the rubric to each generated HTML output. Prior work has shown that large language models can act as structured evaluators when given well-defined scoring rules, producing judgments that correlate with human assessment across multiple domains (e.g., Judging LLM-as-a-Judge with MT-Bench and Chatbot Arena ; When AIs Judge AIs: The Rise of Agent-as-a-Judge Evaluation for LLMs ). We follow this paradigm by defining obligation-level scoring rules grounded in WCAG and applying them consistently at scale.

To check the validity of this procedure, one author manually scored a stratified sample of generated components across multiple component types and prompting conditions using the same rubric. Agreement between manual and automated scores was used to confirm that the rubric yields sensible values on representative outputs.

Experimental design and number of generations

We evaluate 7 providers, 3 prompting conditions, 5 linguistic variants, and 58 components. This yields 7 × 3 = 21 provider–prompt combinations; 21 × 5 = 105 provider–prompt–variant conditions; and 105 × 58 = 6,090 unique component–condition pairs. Because model outputs vary across runs, we generate each pair 10 independent times, for a total of 60,900 HTML outputs.

Scoring and normalization

For each generated HTML output, we score every applicable obligation for that component on the 0–5 scale above, then sum those obligation scores to obtain a single raw score for that output. Because different components have different numbers of applicable obligations, raw totals are not directly comparable across components.

To support comparison (e.g., “email fields are generated more accessibly than text fields”), we normalize each output’s raw score by the maximum attainable score for that component. This produces a normalized score in [0, 1], where 1 means all applicable obligations were met at the highest level.

How the normalized score is computed (shown for transparency)

Let K be the number of applicable obligations for a component, and each obligation score lie in [0, 5]. The maximum attainable score for that component is 5K. The normalized score divides the raw total by 5K. We compute mean and standard deviation over the 10 repetitions for each component–condition pair using R.

Quantity Definition Interpretation
Raw score sum of obligation scores Total semantic quality for one generated output.
Max score 5 × K Maximum possible total given the component’s applicable obligations.
Normalized score raw / (5 × K) Comparable across components; ranges from 0 to 1.

Mean and variability across repeated generations

For each component–condition pair, we compute the mean normalized score across the 10 independent generations and the standard deviation to capture variability. This yields an expected accessibility score for that condition plus a measure of how stable the model is when asked to produce the same component repeatedly. All summary statistics are computed in R.

Step-by-step evaluation pipeline

Step 1 Generate HTML for a target form component under a fixed condition (provider/model × prompt structure × linguistic variant).

Step 2 Score all applicable semantic obligations for the output on a 0–5 scale and sum them to obtain a raw component score.

Step 3 Normalize the raw score by the component’s maximum attainable score so that results fall within [0, 1] and are comparable across components.

Step 4 Repeat Steps 1–3 for 10 independent trials (runs) of the same component under the same condition, producing 10 normalized scores.

Step 5 Compute the mean and standard deviation of these 10 scores in R to estimate expected accessibility performance and variability.
